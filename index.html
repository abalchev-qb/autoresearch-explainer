02The golden rule

METRIC

A command that prints one number.

What you want more (or less) of: coverage %, token count, duplicated-lines %, p95 latency. No clean number → every iteration fails with metric-error and reverts.

GUARD

A command that must stay green.

The behavior you must not break — tests, a type-check, an end-to-end run. The next section lets you feel what happens without one.

06The lesson that outranks the rest

🧭 The grounding gate

These commands are only as good as how well they're anchored in the real code and the real API. A discovery or requirements run that leans on a summary instead of the source will confidently formalize a wrong premise. The highest-leverage habit: no recommendation without first reading the actual entry points and the external contracts it depends on. Often the most valuable output of a discovery run is learning what not to build — before any code is written.

Rule of thumb: match the lens to the code's maturity. On experimental or complex code, the code-grounded lenses (debug, security) have the best signal and are usually under-run. On mature, clean code they mostly confirm health — the marginal value shifts to scenario (robustness gaps) and the optimization loop. (The value of bug/security hunting is proportional to defect density, which tracks how new and complex the code is.) Either way, front-load the grounding:

debug / learn → improve → probe → security → plan → autoresearch (build)

09Five ways teams get it wrong

Loop with no guard.

Silent behavior regressions — exactly what §03 shows.

A metric that isn't a number.

Every iteration reverts with metric-error.

Skipping the grounding gate.

A run on a summary confidently scopes the wrong thing.

Using fix when you mean debug.

Fix crushes errors; debug finds why.

"It exists" ≠ "fit for purpose".

A dormant capability may be stale. Verify before reusing.

Deleting "dead" code a loop flagged.

May be feature-flagged/experimental. Gate removals through a human.
