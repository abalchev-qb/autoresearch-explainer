02The golden rule

METRIC

A command that prints one number.

What you want more (or less) of: coverage %, token count, duplicated-lines %, p95 latency. If Verify doesn't emit a clean number, every iteration fails with metric-error and reverts.

GUARD

A command that must stay green.

The behavior you must not break — your tests, a type-check, an end-to-end run. Without it the loop makes the metric look better while quietly breaking the product. You saw this in §01.

04The lesson that outranks the rest

🧭 The grounding gate

These commands are only as good as how well they're anchored in the real code and the real API. A discovery or requirements run that leans on a summary instead of the source will confidently formalize a wrong premise. The single highest-leverage habit: no recommendation without first reading the actual entry points and the external contracts it depends on. Often the most valuable output of a discovery run is learning what not to build — before any code is written.

A rule of thumb on which lenses to lean on

On an existing codebase, the code-grounded lenses (debug, security) tend to have the best signal-to-noise and rarely run out of things to find — they're usually under-run. The discovery/requirements lenses (improve, probe) saturate quickly and are the most sensitive to grounding. So front-load the grounding:

debug / learn — ground in the real code→ improve — find direction→ probe — vet it→ security — pre-ship→ plan — sequence it→ autoresearch — build it

07Five ways teams get it wrong

Loop with no guard.

Silent behavior regressions. The metric looks great; the product breaks.

A metric that isn't a number.

Every iteration reverts with metric-error. Verify must print one clean value.

Skipping the grounding gate.

A discovery run on a summary instead of the source will confidently scope the wrong thing. Read real entry points first.

Reaching for fix when you mean debug.

Fix crushes errors to zero; debug finds why they happen.

Treating "it already exists" as "fit for purpose".

A dormant capability may be stale or inadequate. Verify it's live and good enough before reusing.

Deleting code a loop flagged as "dead".

It may be intentionally unused — feature-flagged or experimental. Gate removals through a human.
