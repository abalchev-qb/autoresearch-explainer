Autoresearch An autonomous engine that improves code by running one loop, over and over: modify → verify → keep / discard — against a number you choose.

The hard part isn't the loop. It's choosing the right metric to optimize and the right guard to protect. This page lets you play the loop, see why the guard matters, and learn which of the 12 commands to reach for. Built in the spirit of Simon Willison's interactive explanations.

02The golden rule

METRIC

A command that prints one number.

The thing you want more (or less) of. Coverage %, token count, duplicated-lines %, p95 latency. If Verify doesn't emit a clean number, every iteration fails with metric-error and reverts.

GUARD

A command that must stay green.

The behavior you must not break — your test suite, a type-check, an end-to-end run. Without it, the loop will happily make the metric look better while quietly breaking the product. You saw this in §01.

06Five ways teams get it wrong

Loop with no guard.

Silent behavior regressions. The metric looks great; the product breaks.

A metric that isn't a number.

Every iteration reverts with metric-error. Verify must print one clean value.

Running on a dirty or shared branch.

Per-step commits collide. Give each loop its own worktree.

Reaching for fix when you mean debug.

Fix crushes errors to zero; debug finds why they happen.

Deleting code a loop flagged as "dead".

It may be intentionally unused — feature-flagged or experimental. Gate removals through a human.

Optimizing prompt quality with no golden set.

You overfit to nothing. Build the fixtures first, then loop.
